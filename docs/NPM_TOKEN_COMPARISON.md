# 🔐 NPM Token: Granular vs Classic

**Рекомендация:** Используйте **Granular Access Token** для CI/CD

---

## 📊 Сравнение типов токенов

| Характеристика | Granular Access Token ✅ | Classic Token ❌ |
|----------------|-------------------------|------------------|
| **Безопасность** | Высокая | Низкая |
| **Доступ к пакетам** | Конкретные пакеты | Все пакеты аккаунта |
| **Срок действия** | Настраивается | Бессрочный |
| **Ограничение операций** | Да (read/write) | Нет |
| **Для CI/CD** | ✅ Рекомендуется | ⚠️ Не рекомендуется |
| **Ротация** | Легко (срок истечения) | Сложно |
| **Аудит** | Детальный | Базовый |

## ✅ Granular Access Token (рекомендуется)

### Преимущества:

**1. Принцип минимальных привилегий:**
```
✅ Доступ только к @mazix/n8n-nodes-converter-documents
✅ Только операция publish (не delete, не deprecate)
✅ Только на 1 год (потом обновить)
```

**2. Безопасность:**
```
✅ Если токен утечет:
   - Злоумышленник получит доступ только к одному пакету
   - Не сможет удалить пакет
   - Токен истечет через год
   
❌ Если утечет Classic Token:
   - Доступ ко ВСЕМ пакетам аккаунта
   - Может удалить/изменить любой пакет
   - Токен действует бессрочно
```

**3. Управление:**
```
✅ Четкое название: "GitHub Actions CI/CD"
✅ Видно для какого пакета
✅ Видно срок истечения
✅ Легко отозвать конкретный токен
```


## 🔄 Classic Token (устаревший)

### Когда можно использовать:

```
⚠️ Только если:
- У вас старый аккаунт без поддержки Granular Tokens
- Нужна совместимость с очень старыми инструментами
- Временное решение (с планом миграции)
```

### Недостатки:

**1. Безопасность:**
```
❌ Полный доступ ко всему аккаунту
❌ Может публиковать любые пакеты
❌ Может удалять пакеты
❌ Может изменять настройки
❌ Бессрочный (нет автоматического истечения)
```

**2. Управление:**
```
❌ Сложно отследить где используется
❌ Нет ограничений по операциям
❌ Рискованно для CI/CD
```

**3. Соответствие best practices:**
```
❌ Не соответствует принципу минимальных привилегий
❌ Не рекомендуется GitHub/npm
❌ Сложнее проходить security аудиты
```

## 🛡️ Рекомендации по безопасности

### Для Granular Token:

**1. Название:**
```
✅ Хорошо: "GitHub Actions CI/CD - n8n-converter"
✅ Хорошо: "CI/CD Token - Expires 2026-10-09"
❌ Плохо: "token1"
❌ Плохо: "my-token"
```

**2. Срок действия:**
```
✅ 365 дней - баланс удобства и безопасности
✅ 90 дней - если высокие требования безопасности
❌ Бессрочный - избегайте
```

**3. Права:**
```
✅ Read and write - минимум для publish
❌ НЕ давайте больше прав чем нужно
```

**4. Пакеты:**
```
✅ Только конкретный пакет
❌ НЕ выбирайте "All packages"
```

## 📅 Ротация токенов

### График обновления:

```
Granular Token (365 дней):
├─ Создан: 2025-10-09
├─ Напоминание: 2026-09-09 (за месяц)
├─ Истекает: 2026-10-09
└─ Действие: Создать новый токен

Classic Token (бессрочный):
├─ Создан: ???
├─ Проверка: Каждые 6 месяцев
├─ Рекомендация: Перейти на Granular
└─ Действие: Ротация вручную
```

### Процесс ротации:

```bash
# 1. Создать новый Granular Token на npmjs.com
# 2. Обновить в GitHub Secrets
GitHub → Settings → Secrets → NPM_TOKEN → Update

# 3. Проверить работу
git tag v1.0.13-test
git push origin v1.0.13-test

# 4. Удалить старый токен на npmjs.com
npmjs.com → Access Tokens → Revoke old token
```

## 🔍 Проверка токена

### После создания:

```bash
# Тест токена локально (опционально)
echo "//registry.npmjs.org/:_authToken=YOUR_TOKEN" > ~/.npmrc
npm whoami
# Должно показать ваш username

# Очистка
rm ~/.npmrc
```

### В GitHub Actions:

```yaml
# Токен используется так:
- name: Publish to npm
  run: npm publish --access public
  env:
    NODE_AUTH_TOKEN: ${{ secrets.NPM_TOKEN }}
```

## ❓ FAQ

### Q: Можно ли использовать один токен для нескольких пакетов?

**A:** Да, но лучше создать отдельные токены:
```
✅ Рекомендуется:
   - Token 1: @mazix/package-1
   - Token 2: @mazix/package-2

⚠️ Можно, но не рекомендуется:
   - Token 1: @mazix/package-1, @mazix/package-2
```

### Q: Что делать если токен истек?

**A:** Создать новый и обновить в GitHub Secrets:
```
1. npmjs.com → Create new Granular Token
2. GitHub → Settings → Secrets → Update NPM_TOKEN
3. Готово (следующий релиз будет использовать новый токен)
```

### Q: Что делать если токен утек?

**A:** Немедленно отозвать:
```
1. npmjs.com → Access Tokens → Revoke token
2. Создать новый токен
3. Обновить в GitHub Secrets
4. Проверить логи npm на подозрительную активность
```

### Q: Нужно ли обновлять токен в каждом workflow?

**A:** Нет, токен хранится в GitHub Secrets один раз:
```
GitHub Secrets: NPM_TOKEN (один токен)
    ↓
Доступен во всех workflows:
    - release.yml ← использует
    - manual-publish.yml ← использует (если есть)
    - и т.д.
```

## ✅ Checklist создания токена

### Перед созданием:
- [ ] Определены пакеты для доступа
- [ ] Определен срок действия (365 дней)
- [ ] Подготовлено название токена

### При создании:
- [ ] Выбран Granular Access Token
- [ ] Указано понятное имя
- [ ] Выбран конкретный пакет (не "All packages")
- [ ] Выбраны права: Read and write
- [ ] Указан срок: 365 дней
- [ ] Токен скопирован и сохранен безопасно

### После создания:
- [ ] Токен добавлен в GitHub Secrets как NPM_TOKEN
- [ ] Проведен тестовый publish
- [ ] Старый токен удален (если была замена)
- [ ] Добавлено напоминание о ротации через год
