# Исправление ошибки обновления community package из 1.2.2

Дата инцидента: 12 августа 2026 года<br>
Документ зафиксирован: 13 августа 2026 года<br>
Пакет: `@mazix/n8n-nodes-converter-documents`<br>
Исправленная версия: `1.4.3`

## Итог

Обновление пакета с `1.2.2` до `1.4.3` через интерфейс n8n успешно установилось на рабочем LXC-контейнере. Ошибка `The specified package could not be loaded` устранена для сценария обновления без перезапуска процесса n8n.

Победа подтверждена фактической установкой `1.4.3` пользователем после публикации пакета.

Связанные материалы:

- [GitHub Release v1.4.3](https://github.com/mazixs/n8n-node-converter-documents/releases/tag/v1.4.3)
- [Пакет в npm](https://www.npmjs.com/package/@mazix/n8n-nodes-converter-documents/v/1.4.3)
- Коммит исправления: [`3536c3e`](https://github.com/mazixs/n8n-node-converter-documents/commit/3536c3e)

## Исходная ошибка

В интерфейсе n8n обновление с `1.2.2` завершалось сообщением:

```text
Problem updating package
Error updating package "@mazix/n8n-nodes-converter-documents":The specified package could not be loaded
```

Сообщение интерфейса скрывало исходную причину. Реальная причина была видна только в журнале systemd:

```text
ENOENT: no such file or directory, open
'/.n8n/nodes/node_modules/@mazix/n8n-nodes-converter-documents/node_modules/officeparser/node_modules/yauzl/index.js'
```

После сбоя n8n корректно откатывал установку, поэтому установленная версия оставалась `1.2.2`, а сервис продолжал работать.

## Окружение, где воспроизведена ошибка

- виртуализация: LXC, не Docker;
- хост контейнера: `n8n-debian`;
- n8n: `2.34.4`;
- Node.js: `v24.19.0`;
- запуск n8n: systemd-сервис, один долгоживущий процесс;
- каталог community packages: `/.n8n/nodes`.

LXC не был источником ошибки. Он только позволил воспроизвести тот же долгоживущий процесс Node.js и тот же механизм обновления, который используется self-hosted n8n.

## Как работает обновление в n8n

В версии n8n `2.34.4` обновление community package выполняется примерно так:

1. пакет скачивается через `npm pack`;
2. архив распаковывается в каталог community package;
3. из `package.json` удаляются `devDependencies`, `peerDependencies` и `optionalDependencies`;
4. зависимости устанавливаются с параметрами `--install-strategy=shallow`, `--ignore-scripts=true` и без lock-файла;
5. старый пакет выгружается из текущего процесса;
6. новый пакет загружается тем же процессом Node.js;
7. при ошибке n8n восстанавливает резервную копию старой установки.

Ключевая особенность — процесс Node.js не перезапускается. Поэтому одинаковые имена пакетов и уже разрешённые пути модулей могут связывать новую загрузку со старой структурой каталогов.

## Причина по этапам

### 1.4.0: несовпадение экспортируемого класса

В `1.4.0` имя файла узла стало `ConvertFileToJson.node.js`, но экспорт класса не совпадал с именем, которое ожидает загрузчик n8n. Это было исправлено в `1.4.1`:

- добавлен экспорт `ConvertFileToJson`;
- сохранён алиас `FileToJsonNode` для обратной совместимости;
- добавлен тест контракта экспорта.

### 1.4.2: изменившиеся точки входа зависимостей

После исправления экспорта обновление прошло дальше, но обнаружились старые пути двух зависимостей:

- `file-type` в старой версии имел `index.js`, а новая версия использует другую структуру и ESM-точку входа;
- `node-html-parser` в старой версии имел `dist/index.js`, а новая версия использует другую точку входа.

Для них в `1.4.2` были введены новые имена установки:

- `file-type-modern` → `file-type@22.0.1`;
- `node-html-parser-modern` → `node-html-parser@9.0.0`.

Для `file-type` также добавлен небольшой ESM-мост, чтобы CommonJS-файл узла мог использовать ESM-only выпуск зависимости.

### 1.4.3: вложенный `officeparser/node_modules/yauzl`

На существующей установке `1.2.2` структура была такой:

```text
officeparser/
└── node_modules/
    └── yauzl/
        └── index.js
```

При установке нового набора зависимостей npm разместил `yauzl` на уровне community package:

```text
node_modules/
└── yauzl/
    └── index.js
```

Код `officeparser` всё ещё загружался из прежнего пути, а загрузчик Node.js пытался открыть сохранённый старый путь `officeparser/node_modules/yauzl/index.js`. Файл уже отсутствовал, поэтому n8n получал `ENOENT` и показывал общее сообщение о невозможности загрузки пакета.

В `1.4.3` исправление сделано тем же способом, который уже подтвердил себя для других зависимостей:

- `officeparser-modern` → `officeparser@6.0.7`;
- импорт `parseOffice` переведён на `officeparser-modern`;
- старое имя `officeparser` больше не используется production-кодом при загрузке обновлённого узла.

Новое имя создаёт новый путь разрешения модуля и не пересекается с уже закешированным путём старой установки.

## Вывод для будущих релизов

Для community package, который обновляется в уже работающем n8n без перезапуска, недостаточно проверить только чистую установку npm. Обязательна проверка перехода в одном процессе:

```text
старая опубликованная версия
→ существующая структура node_modules
→ обновление штатным алгоритмом n8n
→ загрузка нового узла тем же процессом Node.js
```

Если меняются `main`, `exports`, имя файла узла или расположение точки входа любой production-зависимости, нужно либо сохранить старый путь, либо использовать новый алиас имени зависимости и добавить регрессионный тест на in-place update.

## Пострелизное продолжение: PDF и Markdown в `1.4.4`

После установки `1.4.3` на том же LXC обнаружились два отдельных пользовательских симптома:

1. PDF выдавал `The API version "5.5.207" does not match the Worker version "5.4.530"`.
2. Файл `md` отклонялся как `Unsupported file type: md`.

### Причина PDF-ошибки

Чистый запуск `officeparser@6.0.7` с `pdfjs-dist@5.5.207` обрабатывает PDF нормально. Ошибка появляется только в одном процессе после последовательности:

```text
старый officeparser@6.0.4 + pdfjs-dist@5.4.530
→ разбор PDF
→ загрузка обновлённого officeparser-modern@6.0.7 + pdfjs-dist@5.5.207
→ повторный разбор PDF
```

Старый PDF.js оставляет обработчик `globalThis.pdfjsWorker`. Новый PDF.js обнаруживает его и использует старый `WorkerMessageHandler`, поэтому API `5.5.207` связывается с worker `5.4.530`. Это не связано с LXC, Docker или Node.js `24.19.0`: LXC лишь позволил воспроизвести реальный сценарий обновления без перезапуска процесса.

### Первое исправление PDF в `1.4.4`

В `1.4.4` `src/helpers.ts`:

- разрешает `pdfjs-dist/legacy/build/pdf.worker.mjs` через `createRequire(__filename)`, что поддерживает и вложенные, и поднятые npm-зависимости;
- перед разбором временно очищает устаревший `globalThis.pdfjsWorker`;
- после успеха или ошибки восстанавливает прежний обработчик, чтобы не ломать старые community nodes;
- сериализует вызовы PDF-разбора, исключая гонку при изменении глобального обработчика.

На LXC это прошло проверку для сценария, в котором старый worker оставался только в глобальном обработчике. Однако последующая проверка полного состояния работающего процесса показала, что одного этого слоя недостаточно: PDF.js мог заранее сохранить старый обработчик во внутреннем кэше `PDFWorker`.

### Исправление Markdown

Добавлены стратегии `md` и `markdown`, использующие тот же безопасный декодер текста, что и `txt`. Поэтому Markdown-файлы теперь принимаются по расширению даже когда `file-type` не возвращает сигнатуру текстового файла. Содержимое сохраняется как Markdown-текст.

### Регрессионные проверки

- сначала добавлены красные тесты на worker-конфигурацию и стратегию `md`;
- после исправления прошли focused-тесты helpers/strategies, тесты node version 6, линтер, TypeScript и сборка;
- отдельно на LXC воспроизведён и закрыт конфликт API/worker в одном процессе.

## Пострелизная коррекция: `1.4.5`

Пользовательская проверка `1.4.4` показала, что PDF всё ещё выдаёт:

```text
[OfficeParser]: The API version "5.5.207" does not match the Worker version "5.4.530"
```

При этом Markdown уже обрабатывался. Это разделяет проблему на два независимых участка: маршрутизация Markdown в `1.4.4` исправлена, а PDF.js требовал дополнительной коррекции.

### Подтверждённая причина

В работающем процессе n8n через Node inspector было проверено:

- загруженный новый API PDF.js имел версию `5.5.207`;
- `globalThis.pdfjsWorker` содержал старый `WorkerMessageHandler` с версией `5.4.530`;
- даже при очистке глобального обработчика `PDFWorker._setupFakeWorkerGlobal` уже содержал старый обработчик `5.4.530`;
- установка актуального `GlobalWorkerOptions.workerSrc` сама по себе этот внутренний кэш не заменяла.

Поэтому прежнее объяснение было неполным: проблема была не только в глобальном worker, а в сохранённом внутри PDF.js результате инициализации fake worker. LXC и Node.js `24.19.0` не являются причиной; они позволили наблюдать переход без перезапуска процесса.

### Исправление в `1.4.5`

Перед каждым PDF-разбором `src/helpers.ts` теперь:

1. временно изолирует устаревший `globalThis.pdfjsWorker`;
2. загружает `pdf.mjs` и `pdf.worker.mjs` из текущего пакета;
3. заменяет внутренний кэш `PDFWorker._setupFakeWorkerGlobal` на `WorkerMessageHandler` из текущего worker;
4. передаёт тот же актуальный путь worker в `officeparser`;
5. восстанавливает глобальное состояние после завершения разбора.

Регрессионный тест воспроизводит точное состояние: сначала в кэш нового PDF.js помещается worker `5.4.530`, затем вызывается стратегия PDF. Кандидат заменяет его на `5.5.207` и успешно извлекает текст из PDF на LXC.
