# Переход на officeparser 8

Документы (PDF, DOCX, PPTX, ODT, ODP, ODS, а теперь и RTF) разбирает `officeparser` 8.4.0 вместо 6.0.7. Ниже — то, что не видно из кода и что легко сломать при следующем обновлении.

## Почему алиас `officeparser-v8`, а не `officeparser-modern`

Работающий n8n обновляет community-пакет без перезапуска. Кэш `require` он для пакета чистит, а кэш ESM-модулей Node не сбрасывается до перезапуска процесса. Новое имя пакета даёт новые пути разрешения, и ни один модуль прошлой версии ноды не подменяет собой новый (подробнее про механику — в [истории 1.4.3–1.4.5](./2026-08-12-in-place-update-1.4.3.md)).

## Почему `pdfjs-dist` больше не прямая зависимость

До 1.5.0 включительно `pdfjs-dist` 5.5.207 лежал в корне пакета и грузился как ESM. Если бы новая версия положила pdf.js по тому же пути, процесс n8n получил бы из ESM-кэша старый API 5.5.207 рядом с новым worker'ом — та же ошибка «API version does not match the Worker version», что в 1.4.4.

n8n ставит пакет с `--install-strategy=shallow`: прямые зависимости — в корень, их собственные — внутрь каждой. Поэтому `pdfjs-dist` объявлен только у officeparser и оказывается в `officeparser-v8/node_modules/pdfjs-dist`, по пути, которого не было ни в одной прошлой версии. Тест `test/unit/dependency-versions.test.ts` следит, чтобы прямая зависимость не вернулась.

**Правило на будущее.** Если новая версия officeparser приносит другую версию `pdfjs-dist`, алиас нужно переименовать (например, в `officeparser-v8-5`). Иначе после обновления на лету API pdf.js придёт из ESM-кэша старым, а worker в отдельном процессе прочитается с диска новым.

## Отдельный процесс pdf.js и глобальный worker

officeparser 8 запускает worker pdf.js в отдельном процессе Node с лимитом памяти (1 ГБ) и бюджетом процессорного времени (5 с плюс 20 мс на КБ файла). Он делает это, только если:

- `pdfWorkerSrc` — адрес `file:`; `src/helpers.ts` берёт его из той же копии `pdfjs-dist`, что грузит сам officeparser;
- `globalThis.pdfjsWorker` пуст.

Второе условие важно для обновления на лету: worker pdf.js 5.5.207, загруженный версией 1.5.0, остаётся в `globalThis.pdfjsWorker`. officeparser принял бы его за предзагруженный вызывающим кодом и разобрал PDF им — в этом процессе и с чужой версией API. Поэтому хелпер на время разбора PDF очищает глобал и возвращает его после, а разборы PDF идут по одному.

Сброс кэша `PDFWorker._setupFakeWorkerGlobal` из 1.4.5 удалён: модуль `pdf.worker.mjs` при загрузке сам записывает `globalThis.pdfjsWorker`, так что его загрузка перед разбором навсегда перевела бы officeparser на разбор в нашем процессе, без лимитов. Тест изоляции в `test/unit/helpers.test.ts` это ловит.

`test/integration/in-place-update-load.test.ts` воспроизводит обновление 1.5.0 → текущая версия: прогревает ESM-кэш заглушками pdf.js 5.5.207 (API и worker с глобалом), ставит настоящий officeparser с вложенными зависимостями и разбирает `test/samples/sample3.pdf`. Если убрать очистку глобала, тест падает с «Setting up fake worker failed: stale pdf.js 5.5.207 worker used».

## Предупреждения вместо молчаливой обрезки

У officeparser 8 есть встроенные бюджеты (текстовые элементы и время для PDF, повторяющееся содержимое и ячейки для офисных форматов). Превысив бюджет, он не падает, а возвращает прочитанное и пишет предупреждение в `ast.warnings`. Хелпер пробрасывает предупреждения о потерянном или недостоверном тексте в `warning` результата стратегии в виде `КОД: сообщение`. Если предупреждений нет, ключа `warning` нет, поэтому вывод v5 для обычного файла не меняется.

Бюджеты пока не вынесены в Advanced Options v6 — это следующий шаг.

## Объём установки

officeparser 8 объявляет `tesseract.js` обычной зависимостью и поставляет браузерные бандлы, поэтому пакет стал больше. Наш OCR от этого в UI-установках не заработает: `pdf-to-img` и `tesseract.js` нужны ему из корня пакета, а n8n вырезает наши `optionalDependencies`.
